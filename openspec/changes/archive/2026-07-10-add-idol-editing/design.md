## Context

当前版本的 `idols` 表已经有自增 `id`，`records` 也通过 `idol_id` 关联偶像；但产品规格和部分代码语义仍把 `(name, color, group_name)` 当作偶像本体。结果是用户遇到换团、换应援色、改名或录错资料时，只能新建偶像，已有记录和统计会被拆开。

本变更是在现有离线 SQLite 数据上做兼容扩展：不重建 records，不引入账号或云同步。核心是让 `idols.id` 成为本机业务身份，把三元组降级为“当前展示资料”，并新增 `idols.stable_id` 作为 CSV 里的对外稳定身份。

## Goals / Non-Goals

**Goals:**

- 允许用户编辑已有偶像的名字、团体、应援色。
- 编辑后保留同一个 `idols.id`，所有 `records.idol_id` 不变。
- 为每个偶像生成并持久化 `stable_id`，用于 CSV 导入导出识别同一个偶像。
- 编辑后主界面卡片、详情页、统计、CSV 导出使用新的当前资料。
- 新 CSV 导入优先通过 `stable_id` 查找偶像；旧 CSV 没有 `stable_id` 时仍通过三元组查找或创建偶像。
- 防止两个现存偶像拥有完全相同的当前三元组。

**Non-Goals:**

- 不做偶像合并/拆分工具。
- 不记录完整历史身份时间线。
- 不把 SQLite 自增 `id` 暴露为 CSV 对外身份。
- 不允许创建没有切奇记录的空偶像。
- 不改变 records 的删除策略、去重键或活动关联语义。

## Decisions

### D1. 使用 `idols.id` 作为偶像本体身份

**决定:** 业务上把 `idols.id` 视为偶像本体，名字、团体、应援色只是该偶像当前资料。编辑偶像时只更新 `idols` 行，不迁移或复制 `records`。

**为什么:** 这最贴近游戏客户端里的“角色 GUID + 可变配置字段”模型。记录已经通过 `idol_id` 指向偶像，因此保留 id 可以自然保留全部历史记录和统计。

**候选对比:**

- 继续使用三元组作为身份：实现简单，但换团/换色一定拆统计，无法满足需求。
- 新增 profile/history 表：更完整，但第一版复杂度高，还会牵涉按日期显示历史资料的问题。
- 当前方案：改动集中，兼容现有数据，满足编辑需求。

### D2. 保留当前三元组唯一性作为冲突保护

**决定:** 同一时刻不允许两个偶像拥有完全相同的 `(名字, 应援色, 团体)`。新建偶像和编辑偶像都必须检查该三元组是否已被其他 `idols.id` 占用。

**为什么:** 这保留了当前版本“完全相同三元组不可重复”的用户体验，也避免 CSV 导入时无法判断应该追加到哪一个偶像。

**候选对比:**

- 允许完全重复三元组：更自由，但 UI 和导入都会产生歧义。
- 使用名字唯一：会误伤同名不同团的情况。
- 当前方案：只拦截完全相同的当前资料，仍允许同名或同色偶像共存。

### D3. 第一版只编辑当前资料，不保存历史身份

**决定:** 本变更不新增 `idol_profiles` 或 `idol_history` 表。编辑后的资料覆盖 `idols.name/color/group_name`。

**为什么:** 用户当前的主要痛点是修正和延续同一偶像统计，而不是按过去日期显示旧团体或旧应援色。覆盖式编辑对现有界面、统计、CSV 都更直观。

**候选对比:**

- 新增历史表并按 records.date 显示当时身份：真实但复杂，需要处理日期范围、空范围、历史编辑 UI。
- 覆盖当前资料：简单稳定，后续如果要做历史，可以再从当前资料模型演进。

### D4. CSV 继续使用可见三元组，不新增隐藏 id

**决定:** CSV 导出新增 `偶像ID` 列，写入 `idols.stable_id`，同时继续写当前 `name/color/group_name`。CSV 导入优先按 `stable_id` 查找偶像；没有 `stable_id` 的旧 CSV 继续按文件里的三元组 `findByTriple`，找不到则创建新偶像。

**为什么:** SQLite 自增 `id` 只在本机数据库内可靠，不能跨导入导出使用。`stable_id` 是专门给 CSV 的外部身份，能在偶像换团、换色、改名后继续识别同一个偶像，同时让旧 CSV 通过三元组 fallback 兼容。

**候选对比:**

- 直接导出 SQLite 自增 `id`：本机重导入可用，但跨设备或重建数据库后可能指向错误偶像。
- 导入时尝试模糊匹配改名前后的偶像：容易误合并同名偶像。
- 当前方案：新 CSV 精确识别，旧 CSV 兼容导入，且不暴露本机内部 id。

### D5. stable_id 找到本地偶像时不自动覆盖当前资料

**决定:** 导入 CSV 时，如果 `stable_id` 找到本地偶像，但 CSV 中的名字、应援色、团体和本地当前资料不同，系统 SHALL 只把 records 导入该偶像，不自动修改本地当前资料。

**为什么:** 用户可能已经在本地把偶像资料改成新团或新应援色；导入一份旧 CSV 不应该把当前资料改回旧值。

**候选对比:**

- 导入时自动覆盖本地资料：看似同步，但旧文件会回滚用户的新资料。
- 弹窗询问每次差异：更完整，但会让 CSV 导入流程复杂很多。
- 当前方案：导入只负责追加/去重记录，资料编辑由用户显式操作。

## Risks / Trade-offs

- [Risk] 覆盖式编辑会让旧 records 在导出时显示新名字/团体/应援色，无法还原“当时所属团体”。  
  Mitigation: 在 UI 和规格中明确这是“当前资料编辑”；历史身份记录作为后续能力，不混入第一版。

- [Risk] 用户可能想把两个已存在偶像合并，但编辑到相同三元组会被拒绝。  
  Mitigation: 错误提示说明“已有相同偶像，当前版本不支持合并”；未来单独设计 merge 功能。

- [Risk] 旧 CSV 没有 `stable_id`，导入改名前的旧文件时仍会因为旧三元组找不到当前偶像而创建一个新偶像。  
  Mitigation: 这是旧格式兼容行为；用户在新版覆盖安装后重新导出的 CSV 会带 `stable_id`，之后可稳定识别。

- [Risk] 新 CSV 增加列后，旧版本 App 可能无法完整理解新版导出文件。  
  Mitigation: 新版本导入兼容旧 CSV；旧版本读取新 CSV 不作为本变更目标。导出文件表头明确包含 `偶像ID`。

- [Risk] 数据库唯一索引和编辑更新同时存在，异常路径可能抛 SQLite constraint。  
  Mitigation: Repository 先查询冲突并给出中文提示；DB 约束作为最后防线。

## Migration Plan

1. DB schema 增加 `idols.stable_id TEXT`，并为其建立唯一索引。
2. 升级时为所有既有 idols 生成新的 `stable_id`；已有 `id` 和所有 `records.idol_id` 原样保留。
3. 新建偶像时同步生成 `stable_id`。
4. 发布后，覆盖安装会保留数据库；用户在新版导出的 CSV 会包含 `偶像ID` 和编辑后的当前资料。
5. 回滚到旧版本时，旧代码可能不使用 `stable_id`；已编辑后的三元组会作为普通当前资料存在。
