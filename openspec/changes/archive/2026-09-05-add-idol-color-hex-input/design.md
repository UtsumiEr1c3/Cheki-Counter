## Context

`IdolColorField` 是首页新增偶像、活动详情新建偶像和编辑偶像共同使用的应援色组件。其自定义颜色弹窗当前使用 `flutter_colorpicker 1.1.0` 的 `ColorPicker`，关闭透明度并在用户点击“确定”后把草稿颜色规范为不透明 ARGB。依赖版本已经提供可与调色盘双向同步的内置 Hex 输入栏，但当前未启用。

## Goals / Non-Goals

**Goals:**

- 在现有调色盘弹窗内提供 Hex 文本输入路径。
- 输入有效 `#RRGGBB` 后同步调色盘草稿颜色，并沿用“确定”后才通知外层表单的行为。
- 让所有复用 `IdolColorField` 的新增和编辑入口同时获得该能力。
- 用组件测试覆盖有效 Hex 输入、确认提交和颜色值规范化。

**Non-Goals:**

- 不自制新的颜色解析器或颜色选择器。
- 不支持持久化透明度，也不改变颜色名称的填写和校验规则。
- 不改变数据库结构、CSV 格式、预设色列表或偶像三元组唯一性规则。

## Decisions

### D1：启用依赖内置 Hex 输入栏

在现有 `ColorPicker` 上启用 `hexInputBar`，继续设置 `enableAlpha: false`。

**为什么：** 内置输入栏与 `ColorPicker` 的内部 HSV 状态直接同步，用户通过文本输入后，调色盘位置和 `onColorChanged` 草稿颜色会同步更新。相比在弹窗外另建 `TextFormField`，该方案不需要维护控制器、格式化器、校验错误和调色盘重建逻辑，改动范围更小。

**候选对比：** 自制固定 `#` 前缀且严格六位的输入框能收紧格式，但会重复依赖已经提供的解析与同步能力。本变更接受内置输入栏较宽松的兼容格式，并把 `#RRGGBB` 作为主要使用和测试路径。

### D2：保留弹窗草稿与确认提交语义

Hex 输入只更新 `_openColorPicker` 内的 `draftColor`；用户点击“确定”后，组件才把选择结果规范为不透明 ARGB 并调用 `onChanged`。点击“取消”不得改变外层选择。

**为什么：** 这与现有拖动调色盘的交互完全一致，避免文本输入绕过取消操作，也不改变调用方状态管理。

**候选对比：** 输入时立即通知外层表单虽然反馈更早，但会使“取消”无法恢复原值，因此不采用。

### D3：在共享组件层验证一次，覆盖全部入口

组件测试打开 `IdolColorField` 的自定义颜色弹窗，在 Hex 输入栏录入有效的 `#RRGGBB`，确认后断言回调收到对应的不透明 ARGB 色值。

**为什么：** 三个业务入口均复用同一个组件；在组件边界测试可以直接验证新增行为，并避免为相同交互编写重复的完整弹窗流程测试。

**候选对比：** 分别测试新增和编辑弹窗能覆盖更长的集成路径，但本变更不修改调用方，投入与收益不匹配。

## Risks / Trade-offs

- **[输入格式比六位更宽松]** 内置输入栏还接受省略 `#`、三位缩写和八位输入。→ **Mitigation：** 关闭 Alpha，确保最终值仍被规范为不透明 ARGB；规格和测试以 `#RRGGBB` 为标准路径。
- **[弹窗纵向空间增加]** Hex 输入栏可能在小屏幕或键盘弹出时占用额外高度。→ **Mitigation：** 继续使用现有 `SingleChildScrollView` 包裹颜色选择器，允许内容滚动。
- **[依赖内部文案和控件结构影响测试]** 测试若依赖 `Hex` 文案，未来升级依赖时可能需要调整。→ **Mitigation：** 当前锁定 `flutter_colorpicker 1.1.0`，不在本变更中升级依赖，并只对用户可见行为做最小断言。

## Migration Plan

无需数据迁移。发布后所有复用 `IdolColorField` 的入口自动显示 Hex 输入栏；回滚时关闭该配置即可恢复原调色盘，既有颜色数据不受影响。

## Open Questions

无。已确认使用依赖内置输入栏，并接受其兼容输入格式。
