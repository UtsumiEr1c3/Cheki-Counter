## Context

团切目前在 `records.group_name` 保存单个团体，在 `records.group_members` 保存当次成员文本。团体候选会读取历史团切中的团名，但成员预填只读取 `idols` 当前资料；团体统计也依赖 `records.group_name` 精确分组。此次变更需要在保留单条团切计数语义和旧数据的前提下，引入多团体关联并复用最近成员快照。

## Goals / Non-Goals

**Goals:**

- 一条团切可关联一个或多个团体，同时继续只保存一条 `records` 记录。
- 团体选择后复用当前登记成员和最近一次团切快照，减少重复输入。
- 联合团切在活动、总支出和整体切数中只累计一次，在每个参与团体的统计中各归属一次。
- 完整兼容现有数据库与单团体 CSV。

**Non-Goals:**

- 不建立可独立维护的团体主表。
- 不把团切金额拆分或分摊给各团体、成员。
- 不把团切计入个人统计，也不自动修改偶像资料。
- 不保存可复用的命名阵容模板；只使用每个团体最近一次团切快照。

## Decisions

### D1：使用轻量关联表保存团切参与团体

新增 `record_groups(record_id, group_name, position)`，以 `(record_id, group_name)` 保证同一团体不重复，并用 `position` 保留用户选择顺序。`records` 继续保存团切主体及成员快照，旧 `group_name` 字段保留第一个团体作为兼容回退。为什么：一条记录对应多个团体是多值关系，关联表能使用精确匹配完成团体统计，避免分隔字符串产生名称歧义。候选方案是 JSON 或分隔文本字段，会把过滤、去重和迁移逻辑散落到查询与业务代码中；完整团体主表则超过当前需求。

### D2：写入团切时在同一事务中保存记录和关联

`RecordRepository.insert` 在插入团切主体后依次写入团体关联；任一步失败则回滚。删除记录时同步删除关联。为什么：避免出现有团切无团体或残留关联。候选方案是由界面分别调用两次仓库写入，无法保证原子性。

### D3：成员预填合并当前成员与最近快照

每次添加一个团体时，按当前登记成员顺序读取 `idols`，再读取该团最近一条团切的 `group_members`，按首次出现顺序合并去重，并与输入框现有内容合并。移除团体时不自动删除成员，最终内容仍由用户确认。为什么：当前资料可能不完整，最近快照能复用手工补录；保留现有输入可以避免异步查询或继续选团时覆盖用户编辑。候选方案是合并全部历史快照，容易长期累积已离团成员。

### D4：团体统计按关联展开，整体统计仍按记录聚合

团体总览和详情通过 `record_groups` 连接团切记录，所以联合团切在每个参与团体中各出现一次；活动、支出和整体统计继续直接聚合 `records`，只累计一次。为什么：这符合已确认的团体归属口径，同时保持实际支付与拍摄次数不重复。团体列表各行不具备可相加语义，界面不新增跨团体合计。

### D5：CSV 追加多团体列并保留旧团体列

CSV 尾部追加“团切团体”列，以 JSON 字符串数组保存完整团体列表；原“团体”列继续写第一个团体。导入优先读取新列，没有新列时把原“团体”作为单元素列表。为什么：JSON 能无歧义保存包含标点的团名，尾部新增列保持旧文件可读。候选方案是在原列使用顿号分隔，会与合法团名冲突。

## Risks / Trade-offs

- [Risk] 关联表与旧 `group_name` 字段发生不一致 → Mitigation：所有新版写入在同一事务完成，读取优先使用关联表，旧字段只作兼容回退。
- [Risk] 联合团切在多个团体行中各计一次，用户手工相加会大于整体支出 → Mitigation：整体汇总始终直接聚合记录，团体页不提供跨团体合计。
- [Risk] 最近快照包含已经离团成员 → Mitigation：成员字段保持可编辑，只取最近一条历史快照并允许删除。
- [Risk] 删除记录后遗留团体关联 → Mitigation：仓库删除流程显式先删关联，并在表定义中保留级联约束。

## Migration Plan

数据库版本从 v9 升至 v10，创建 `record_groups` 及团名索引，并把每条现有团切的非空 `records.group_name` 写为位置 0 的关联。新安装直接创建关联表。应用回滚到旧版本时仍可读取每条团切的第一个团体，但联合团切的额外团体不可见；回滚前应通过新版 CSV 备份。
