## Context

活动总览目前根据 `records.is_online` 动态排除活动，导致删除最后一条电切记录后活动分类改变。`events` 只有本地自增主键，CSV 通过名称、场地、日期匹配活动；活动改名后无法跨导入稳定识别。现有统计分别覆盖全部切奇金额和现场活动金额，缺少将全部切奇与现场门票组合后的统一支出视图。

## Goals / Non-Goals

**Goals:**

- 活动参与方式独立持久化，删除记录不改变活动分类。
- 提供按年统计的完整支出视图。
- 支持安全编辑活动并保持关联记录一致。
- 新版 CSV 保存稳定活动身份和参与方式，同时兼容所有旧格式。

**Non-Goals:**

- 不实现删除活动。
- 不支持自动合并重复活动。
- 不增加现场与电切混合参与方式的专门入口。

## Decisions

### D1：在 `events` 保存 `stable_id` 和 `is_online`

`stable_id` 用于 CSV 往返识别，`is_online=0` 表示现场参加，`is_online=1` 表示仅电切。为什么：活动分类属于活动自身事实，不应由当前记录集合推导；稳定 ID 可以让活动改名后仍能被新版 CSV 识别。候选方案是继续根据记录推断，无法解决删除记录后分类漂移和改名后的导入重复。

### D2：记录继续保留 `is_online`

活动参与方式用于活动筛选、参加场数和门票统计；记录参与方式用于区分现场切与电切金额。为什么：两者统计维度不同，旧数据也已经依赖记录标记。候选方案是只保留活动标记，会丢失无活动记录的电切属性，也无法兼容历史混合数据。

### D3：编辑活动按 ID 更新，并有条件同步记录日期和场地

编辑保存时保持活动 ID 和稳定 ID 不变。关联记录中日期等于活动旧日期的行同步为新日期；场地等于活动旧场地的行同步为新场地，已有不同值（例如“电切”）的记录保留。为什么：可修正由活动带入的冗余值，同时避免覆盖记录自身明确保存的差异。若新三元组与其他活动冲突，拒绝保存并提示用户。

### D4：支出使用一次聚合查询返回

按记录日期汇总全部切奇、现场切和电切；按活动日期汇总 `is_online=0` 活动的门票与场数。累计支出等于全部切奇费用加现场门票。为什么：可以覆盖无活动记录，门票也不会因多条记录重复累计。候选方案是从活动列表对象在 UI 端相加，会漏掉仅电切和无活动记录。

### D5：CSV 在尾部追加可选字段

新版导出在现有列尾追加“活动ID”和“活动方式”，导入按表头定位新增字段；缺少字段的旧 CSV 继续按原规则处理。新版优先按活动稳定 ID 查找，旧版按三元组查找。为什么：尾部追加对现有格式影响最小，也保持旧文件可导入。旧活动的参与方式由数据迁移统一推断，旧 CSV 新建的纯活动默认现场，只有电切记录的新活动标记为仅电切。

## Risks / Trade-offs

- [旧 CSV 中改名前的活动没有稳定 ID，重新导入可能生成重复活动] → 新版导出携带稳定 ID；编辑冲突时阻止保存，避免进一步扩大重复。
- [无关联记录的历史活动无法推断是否仅电切] → 迁移时按现场参加处理，用户可以在编辑页修正。
- [活动与记录分别保存参与方式，可能出现组合差异] → 新建和选择活动时采用明确默认值，统计严格按字段职责计算，并保留历史记录原值。
- [编辑日期或场地可能影响个人统计] → 只同步仍等于旧活动值的关联记录，并在保存前提示影响范围。

## Migration Plan

数据库从 v6 升至 v7，先增加可空 `stable_id`，为既有活动生成唯一值并建立唯一索引，再增加 `is_online NOT NULL DEFAULT 0`。仅当活动有关联记录且全部为电切时将活动标记为仅电切。新安装直接创建完整 schema。回滚到旧应用时新增列会被忽略，但旧应用仍按记录临时筛选活动。
